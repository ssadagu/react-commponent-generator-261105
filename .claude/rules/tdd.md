# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계 생략, 순서 변경, 예외 임의 추가 금지.

> **우선순위:** 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그쪽이 우선**한다. 이 파일은 기본값(fallback)이다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (핸들러, 클라이언트, 데이터 변환)
- **유틸 함수**
- **버그 수정** (재현 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL (스키마, 마이그레이션)

> 판단이 애매하면 **적용**한다. 로직이 섞인 UI(조건 분기, 상태 계산 등)는 순수 UI가 아니다.

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 마라.
- **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"**이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니다 — 고쳐서 다시 실행.

### GREEN — 통과시키기

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 분기, 옵션은 쓰지 않는다.
- **신규 + 기존 테스트 모두 통과**를 확인한다.

### REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출.
- **green 상태 유지.** 변경 후마다 테스트를 실행한다.
- **새 동작 추가 금지.** 새 동작은 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 반복.

## 3. 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. **삭제한다.**
2. **RED부터 재시작**한다.

- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함.
- 삭제 후 테스트에서 이끌어낸 코드만 인정된다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 끝난다. 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓴 것이라 **항상 통과**한다. 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 TDD보다 오래 걸린다. **TDD가 더 빠르다.** |
| "삭제하면 낭비다" | 매몰 비용 오류다. 검증 안 된 코드를 유지하는 비용이 재작성 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트 없이 **버려라**, 남길 코드라면 테스트부터 써라. |
