# commit

변경사항을 분석해 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다.

## 커밋 메시지 컨벤션

형식: `<type>: <요약>`

| type | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 코드 구조 개선 |
| chore | 빌드, 설정, 의존성, 문서 등 기타 작업 |

규칙:
- 요약은 한국어로, 50자 내외, 마침표 없이 작성한다.
- "무엇을 했는지"를 명확히 쓴다. (예: `feat: 컴포넌트 카드에 복사 버튼 추가`)
- 필요하면 빈 줄 뒤에 본문으로 "왜 변경했는지"를 덧붙인다.

## 절차

### 1. 변경사항 분석
다음 명령을 병렬로 실행한다.
- `git status` — 변경/추적되지 않는 파일 확인
- `git diff` 및 `git diff --staged` — 실제 변경 내용 확인
- `git log --oneline -5` — 기존 커밋 메시지 스타일 참고

변경사항이 없으면 그 사실만 알리고 종료한다.

### 2. 논리적 단위로 분류
- 하나의 목적(기능, 버그 수정, 리팩터링, 설정 등)별로 파일을 묶는다.
- 서로 다른 성격의 변경은 별도 커밋으로 분리한다.
- 같은 파일 안에 성격이 다른 변경이 섞여 있어도 가급적 파일 단위로 나누고, 불가피할 때만 `git add -p`를 쓴다.
- `.env`, 키, 토큰 등 비밀 정보가 포함된 파일은 커밋 대상에서 제외하고 사용자에게 알린다.

### 3. 커밋 계획 제시 및 승인 요청
커밋별로 아래를 보여주고 사용자 승인을 받는다.
- 커밋 메시지 (`type: 요약`)
- 포함될 파일 목록

승인 없이 절대 커밋하지 않는다. 사용자가 수정을 요청하면 반영한 뒤 다시 확인한다.

### 4. 커밋 실행
승인 후 커밋 단위마다 순서대로 실행한다.
- 해당 파일만 명시적으로 `git add <파일>` 한다. (`git add -A`, `git add .` 지양)
- `git commit`으로 커밋한다. 여러 줄 메시지는 HEREDOC을 사용한다.
- 시스템에서 지정한 Co-Authored-By 등 attribution 줄이 있으면 메시지 끝에 추가한다.
- 모든 커밋이 끝나면 `git log --oneline`과 `git status`로 결과를 확인해 보고한다.

## 주의
- push는 사용자가 따로 요청하지 않는 한 하지 않는다.
- `--no-verify`, `--amend`, force 옵션은 사용자가 명시적으로 요청할 때만 사용한다.
- pre-commit hook이 실패하면 원인을 수정하고 새 커밋으로 다시 시도한다.
